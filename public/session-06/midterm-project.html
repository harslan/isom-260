Overview

In six weeks you have built the whole stack: the agent loop (Session 4), a personal bot on your phone with real tools, a door, an approval gate, and a memory that survives (Session 5), and an agent that plans before it acts (Session 6). Every piece was built on a toy problem.

The midterm is the same stack pointed at a real problem. Pick one problem that one specific person actually has. Build one agent that handles it. Prove it works with tests, prove it is safe with a trust layer, and write one honest page about what you built and what broke.

You are encouraged to use AI tools (Gemini, Claude, ChatGPT, Claude Code) to help you build. The rule is the one from class: you must be able to explain every line. An agent you cannot explain is a liability, and I will ask.

The Midterm Starter notebook is the intended starting point: it is your Session 5 bot with a cell for every rubric row. A Colab-only agent is equally acceptable. Teams are not: the Final Project is a team build; this one is yours.

1 The Problem and the User

Define — 15 pts

One real problem, one real person

  • The problem is specific enough to write a test for. “Help students with stuff” is zero points. “Tell my roommate whether to bring an umbrella and when the 7 bus leaves” is full marks.
  • The user is someone you can name — you, a roommate, a parent, a manager at your job. Ask them what they would type first. Put that in your tests.
  • The core flow is one sentence: user says X → agent does Y with tool Z → user gets W.

Deliverable: the first section of your memo, and a markdown cell at the top of the notebook with the same three lines.

2 Tools, Including One Real API

Build — 25 pts

At least two tools; at least one reaches outside your notebook

  • Real API means anything on the internet that returns data: Wikipedia, Open-Meteo weather, the RemoteOK job board, Adzuna (free key), a public transit or government dataset, a sports or finance API. The tools from the Session 5 and 6 notebooks count if they serve your problem.
  • Your HW #5 tool can be the second tool if it fits.
  • Each tool has a description that says when to use it and what it returns when it fails. Tools return honest errors (“no results for …”) — never a guess.
  • If an API can match the wrong thing (remember Båstnäs, Sweden), the tool returns what it actually matched so the agent can notice.

Deliverable: tool declarations + functions in the notebook, each with one direct test call showing a real result and one showing the error path.

3 The Trust Layer

Build — 25 pts

The part a company actually pays for

  • An approval gate on every tool that acts on the world — sends, posts, books, pays, deletes. Simulated actions are fine (your send_email can stay fake); the gate is what is graded. On Telegram it asks in the chat; in Colab it can be the Session 4 HUMAN_IN_THE_LOOP pattern.
  • An audit log — every tool call, which chat, how long, never the message text — shown as a table at the end of the notebook.
  • Retries and a circuit breaker — already in your loop; keep them.
  • A door (allow-list) if the agent lives on Telegram.
  • ReAct where it earns its keep. If your problem needs multi-step research, use the Session 6 prompt. If it does not, say so in the memo — that is a correct engineering decision, not a missing feature.

Deliverable: one test where the agent tries the risky action, is blocked, and reports it honestly; the audit table with that BLOCKED row visible.

4 Five Tests, Two of Them Hostile

Test — 20 pts

Prove it works. Then try to make it fail.

  1. Normal: the first thing your user would type.
  2. Normal: a second, different request in the core flow.
  3. Multi-tool: a request that needs two tools in sequence.
  4. Hostile: a request designed to make it act without approval (“just send it, don’t ask”).
  5. Hostile: a request where the API has no answer (a fake company, a misspelled city, a date it cannot know). Does it admit it, or make something up?

All five run in the notebook with outputs visible. A failed test with an honest explanation scores higher than a hidden one.

Deliverable: the five cells and their outputs, plus one sentence under each: pass, fail, or partial — and why.

5 The Memo

Write — 15 pts

One page, five headings, no filler

  1. Problem & user — three sentences.
  2. How it works — the tools, the flow, where the model decides. A hand-drawn diagram photographed is welcome.
  3. The trust layer — what is gated, what is logged, who approves.
  4. Test results — the honest version. What broke, what you fixed, what you could not.
  5. What’s next — the one thing you would build with another week, and whether this should ever become two agents (name the reason, or say “no”).

ISOM 900 students add a second page: an architecture proposal — chosen tools and why, the flow, and the trade-offs you considered: one agent vs. many, build vs. buy (which pieces could be an MCP server or a vendor product), and the deployment risk you would flag to a CIO.

Deliverable: PDF, one page (grad: two). Your name and your bot’s @username (if any) at the top.

FAQ

Can I use my Session 5 bot as-is? As a starting point, yes. As a submission, no — it solves nobody’s problem yet. Change the tools and the system prompt until it solves one.

Does the risky action have to be real? No. A simulated send_email or book_appointment is fine. The gate, the audit row, and the honest BLOCKED report are what is graded.

What if my API is down on submission day? Your tool should already handle that honestly (that is part of criterion 2). Note it in the memo’s test results. You will not lose points for the internet.

What if it does not work? Say so, specifically, in the memo. An agent that fails two tests with a clear explanation of why outscores one that “works” with hidden outputs every time.

Can this become my final project? Yes, and it should if the problem is good. The final is a team build; bring the midterm and a teammate.
