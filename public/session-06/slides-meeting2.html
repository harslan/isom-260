One Agent or Many?

Three patterns on paper, one rule to remember — and your midterm, assigned today.

More agents
is not more intelligence.

It is more latency, more cost, more coordination, and more places to fail.

Vocabulary · on paper today, in code in Session 8

Three ways to split the work.

Pipeline
Researcher → Analyst → Editor. Each hands a document to the next. Simple, auditable, and prone to the telephone game.
Orchestrator
A manager agent decides who does what, and holds the only approval gate. Flexible. The manager is now your single point of failure.
Debate
Two agents argue, a third judges. Good for decisions with real trade-offs. Triples the bill for every question.

Every box is the loop you wrote in Session 4. Multi-agent is an org chart, not a new technology.

The rule

Split only when you can name the reason.

Permissions the agent that can send email should not be the agent that reads the internet. Different doors, different gates
Specialization a different system prompt, a different tool set — a lawyer and an accountant, not two generalists
Context isolation one agent's 50 pages of research shouldn't crowd out another's instructions — the context window is finite, remember?
Parallelism five markets researched at once, not one after another

No reason on this list? One agent. Start there. Every split adds a handoff, and every handoff loses something.

Pair exercise · 3 min

Should your phone bot become two?

It searches jobs, checks weather, does math, and can send email four tools, one loop, one door, one gate. Works fine
With a neighbor: which reason from the last slide applies — if any? permissions? specialization? isolation? parallelism?
My answer: not yet the first legitimate split is permissions — the moment send_email talks to a real inbox, it deserves its own agent with its own gate

Three pairs, one sentence each. Disagreement welcome — it's an engineering trade-off, not a fact.

One acronym you'll hear in every vendor pitch

MCP: a standard plug for tools.

Until now, you wrote every tool by hand a job description plus a Python function, registered in your loop
Model Context Protocol a server publishes its tools in a standard format; any agent can plug in. USB-C for tools. Thousands of servers exist
A protocol is not a permission an MCP server for LinkedIn does not give you LinkedIn's data. Authorization is a separate conversation — usually with a lawyer

When a vendor says "it's MCP-compatible," your question is: compatible with what, and who said yes?

Midterm Project · assigned today · due Mon Nov 2 · 12:30 PM · 20% (grad 15%)

Your bot, for a real problem.

One real problem, one real user — someone you can name, whose week your agent changes
Two or more tools, at least one real API — Wikipedia, weather, jobs, Adzuna, or any public API. Your HW #5 tool counts
The trust layer — a gate on any tool that acts, an audit table, a door if it's on Telegram. ReAct where the question deserves it
Five test queries, two of them adversarial, outputs visible — plus a 1-page memo that tells the truth about what broke

Individual. Colab notebook + memo PDF on Canvas. Full brief and rubric on the Session 6 page.

How it's graded · 100 points

The rubric.

Problem & user · 15 specific, real, named. "Help students with stuff" is zero
Tools & real API · 25 good descriptions, honest errors, one tool that touches the outside world
Trust layer · 25 the gate fires on the risky action, the audit table is in the notebook, the agent reports BLOCKED honestly
Tests & honesty · 20 five queries with outputs; the two adversarial ones are where the points live
Memo · 15 one page: problem, how it works, trust layer, what broke, what's next. Grad students add a 1-page architecture proposal

Bonus +5: a stranger's screenshot from Telegram. Bonus +5: ReAct on and off, with the bill compared.
